# Jenix FieldForce — Kotlin Capacitor Plugin Phase

The backend phase is COMPLETE.

Your job now is ONLY to build the reusable Android native layer as small Kotlin Capacitor plugins.

## Hard Scope

DO:

* Kotlin native Android
* reusable Capacitor plugins
* TypeScript plugin interfaces
* native background services/workers/receivers
* plugin tests
* plugin documentation
* integration contracts with the existing backend

DO NOT:

* build React UI
* redesign frontend
* rewrite backend
* recreate video calling
* implement cellular call-audio recording
* add unrelated features

An existing native video-call plugin already exists. Reuse/integrate with its events later; DO NOT replace it.

# First Step — Inspect, Don't Invent

Before writing code:

1. Inspect repository structure.
2. Read `BACKEND_HANDOFF.md`.
3. Inspect existing backend routes/types.
4. Inspect existing Capacitor version.
5. Inspect existing Android target/min SDK.
6. Inspect existing video-call plugin.
7. Reuse existing conventions.

# Architecture

Create small reusable packages, not one giant plugin:

```text
@jenix/cap-core
@jenix/cap-location
@jenix/cap-device-health
@jenix/cap-lifecycle
@jenix/cap-push
@jenix/cap-dialer
@jenix/cap-device-policy
```

Each must be independently testable.

All common functionality should live in `cap-core`, not be copied between plugins.

Dependency direction:

```text
cap-core
   ?
   +-- cap-location
   +-- cap-device-health
   +-- cap-lifecycle
   +-- cap-push
   +-- cap-dialer
   +-- cap-device-policy
```

No circular dependencies.

---

# Mandatory Coding Rules

Every handwritten source file MUST remain under 200 lines.

Do not bypass this by minifying code.

Split by responsibility.

Generated files and package lockfiles are exempt.

Prefer:

* Kotlin
* coroutines where appropriate
* AndroidX
* WorkManager where appropriate
* Room/DataStore only where justified
* official Android APIs
* Capacitor standard plugin APIs

Avoid unnecessary dependencies.

No hidden/private Android APIs.

No accessibility-service hacks.

No battery-optimization bypass hacks.

No root requirement.

# 4. `@jenix/cap-lifecycle`

Keep this plugin SMALL.

Responsibilities:

```text
BOOT_COMPLETED handling
MY_PACKAGE_REPLACED handling
app update recovery
network restored signal
native service recovery coordination
```

Expose:

```ts
getLastBootState()
getRecoveryStatus()
```

Do not duplicate the actual location service.

`cap-location` owns location.

`cap-device-health` owns heartbeat.

`cap-lifecycle` only coordinates recovery.

Important:

Modern Android has restrictions on launching foreground services from background/boot receivers.

Follow the current target SDK rules.

Where direct service start is prohibited, use the Android-supported recovery mechanism such as WorkManager instead of hacks.

Never create reboot loops.

# Cross-Plugin Rules

One native responsibility must have ONE owner.

Examples:

```text
LocationForegroundService
? cap-location only

InCallService
? cap-dialer only

FirebaseMessagingService
? cap-push only

Heartbeat
? cap-device-health only
```

Other plugins communicate through small interfaces/shared core state.

Never create competing services for the same responsibility.

# Native Background Sync

Where backend synchronization must continue without React:

```text
Native event
   ?
durable local queue
   ?
native uploader/worker
   ?
existing backend API
   ?
success
   ?
remove queued record
```

Use bounded retry/backoff.

Never create an infinite aggressive retry loop.

Do not lose queued data merely because:

```text
WebView closes
app UI is swiped away
network disappears
phone restarts
```

within what Android legitimately permits.

# TypeScript Contract

Each plugin must have a small typed public API.

No React components.

Example pattern:

```ts
export interface JenixLocationPlugin {
  startTracking(options: TrackingOptions): Promise<void>;
  stopTracking(): Promise<void>;
  getTrackingStatus(): Promise<TrackingStatus>;
  syncNow(): Promise<SyncResult>;
}
```

Keep native implementation details out of React.

Use consistent errors such as:

```text
PERMISSION_DENIED
NOT_CONFIGURED
NOT_SUPPORTED
ROLE_REQUIRED
SERVICE_NOT_RUNNING
NETWORK_UNAVAILABLE
BACKEND_REJECTED
```
